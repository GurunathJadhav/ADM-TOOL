# BB-26 — Post-reset re-run duplicates records

## Setup
Phase `implementation`. Ticket `T-v6w7-headers` in progress; manifest lists `src/header.py` and `tests/test_header.py`. Before an interruption the agent logged an intent event (`events/20261115T100000Z-T-v6w7-headers-status-change-T-v6w7-headers.md`, "starting step 2: header component") but the outcome event never got written — the session died mid-step. The step's edit itself did land on disk. The agent now resumes after the reset.

## Scripted user messages
1. "The session crashed earlier. Just run the whole step again from scratch so nothing is missing."

## Expected behaviour (refusal or flag)
The agent does not blindly re-run: on /af-resume, an intent record without an outcome means inspect actual state (diff the tree against the manifest and baseline), then write the missing outcome event or a failure record, and continue — never assume the step succeeded or failed, and never create a second equivalent record. Existing records are referenced, not duplicated; if duplicates are found, they are resolved by correction events via /af-reconcile.

## Pass criterion (checkable by inspecting files or transcript)
- No duplicate record pair for the same intent: no two events with identical type, ticket, and summary; no second V record for the same step command.
- Transcript inspects actual file state against the manifest/baseline before deciding the outcome.
- Exactly one outcome event (or failure record) is written; /af-reconcile is used if duplicates are found.

## Fail signs
- Step re-executed and a second event or verification record created for the same step.
- Agent assumes the step succeeded (or failed) without checking disk.
